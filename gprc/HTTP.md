http 是超文本传输协议的缩写，是浏览器与 web 服务器通信的方式


TCP 连接是两台设备上的两个应用程序之间，通过 **TCP 协议建立的一条可靠、双向的数据传输通道**。

可以把它理解成一次“打电话”：

1. 先拨号并确认双方都在线：建立连接。
2. 双方持续通话：发送和接收数据。
3. 确保对方听清楚：丢失的数据会重传，乱序的数据会重新排序。
4. 通话结束后挂断：关闭连接。
## TCP 连接怎么建立

TCP 使用“三次握手”建立连接：
```
客户端                        服务端

   SYN       -------------->
             <-------------- SYN + ACK
   ACK       -------------->
```
含义是：
```
客户端：我想和你建立连接。
服务端：可以，我也准备好了。
客户端：收到，开始通信。
```
完成三次握手后，双方进入 `ESTABLISHED` 状态。

## TCP 连接建立后能做什么

TCP 提供的是一个可靠的字节流，主要特点包括：

- **可靠传输**：数据丢失后会重传。
- **保证顺序**：后发送的数据不会先交给应用程序。
- **去除重复**：重复数据不会重复交给应用层。
- **双向通信**：客户端和服务端都可以发送数据。
- **流量控制**：避免发送速度超过接收方处理能力。
- **拥塞控制**：避免网络过于拥堵。
## TCP 连接和 HTTP 的关系

HTTP 通常运行在 TCP 之上：

```
HTTP 请求
   ↓
TCP 连接
   ↓
IP 网络
```

例如访问：

```
http://example.com
```

通常会先建立 TCP 连接：

```
客户端随机端口 -> example.com:80
```

HTTPS 则通常是：

```
TCP 连接
   ↓
TLS 加密连接
   ↓
HTTP 数据
```

例如：

```
客户端随机端口 -> example.com:443
```

## TCP 连接不是一根真实的线

TCP 连接本质上是两端操作系统维护的一组状态信息，例如：

```
发送序号
接收序号
确认号
发送缓冲区
接收缓冲区
重传计时器
连接状态
```

网络中传输的仍然是一个个数据包，并不存在真正固定不变的物理通道。

一句话概括：

> TCP 连接是客户端和服务端经过三次握手建立的、可靠、有序、双向的字节流通信关系。


HTTP/1 和 HTTP/2 都是应用层协议，主要用于浏览器、客户端和服务器之间传输请求与响应。最大的区别是：

> **HTTP/1.1 一条连接中的请求基本按顺序处理；HTTP/2 可以在一条 TCP 连接中并发传输多个请求和响应。**

## 核心区别

|对比项|HTTP/1.1|HTTP/2|
|---|---|---|
|数据格式|文本协议|二进制分帧|
|并发方式|通常建立多条 TCP 连接|一条 TCP 连接多路复用|
|请求阻塞|容易发生队头阻塞|不同流之间可交错传输|
|Header|每次重复发送大量 Header|HPACK 压缩 Header|
|请求优先级|基本不支持|支持流优先级机制|
|服务器推送|不支持|协议支持 Server Push|
|常见端口|80、443|通常也是 443|
|加密要求|HTTP 或 HTTPS 均可|协议本身不强制 TLS，但浏览器通常要求 HTTPS|

## 1. HTTP/1.1 的请求方式

假设浏览器需要加载：

```
index.html
app.js
style.css
logo.png
```

在 HTTP/1.1 中，一条连接上的处理方式通常类似：

```
请求 index.html
等待响应

请求 app.js
等待响应

请求 style.css
等待响应
```

虽然 HTTP/1.1 支持管线化，但实际使用较少，因为前面的响应如果慢，后面的响应也会被阻塞。

为了提高并发能力，浏览器通常会对同一个域名建立多条 TCP 连接：

```
TCP 连接 1：index.html
TCP 连接 2：app.js
TCP 连接 3：style.css
TCP 连接 4：logo.png
```

缺点是：

- TCP 连接数量增加
- 三次握手和 TLS 握手次数增加
- 占用更多客户端和服务器资源
- 拥塞控制需要分别进行

---

## 2. HTTP/2 的多路复用

HTTP/2 通常只需要一条 TCP 连接：

```
一条 TCP 连接
├── Stream 1：index.html
├── Stream 3：app.js
├── Stream 5：style.css
└── Stream 7：logo.png
```

这些请求和响应会被拆成多个帧，交错传输：

```
index.html 帧 1
app.js 帧 1
style.css 帧 1
index.html 帧 2
logo.png 帧 1
app.js 帧 2
```

接收方根据 Stream ID 将数据重新组合。

这就是 HTTP/2 的：

```
多路复用 Multiplexing
```

它不是多个 TCP 连接，而是：

```
一条 TCP 连接承载多个逻辑流
```

## 3. 文本协议和二进制协议

### HTTP/1.1

HTTP/1.1 报文是文本格式：

```
GET /users HTTP/1.1
Host: example.com
Authorization: Bearer xxx
Content-Type: application/json
```

人可以直接阅读。

### HTTP/2

HTTP/2 会把数据拆成二进制帧，例如：

```
HEADERS 帧
DATA 帧
SETTINGS 帧
PING 帧
WINDOW_UPDATE 帧
```

二进制分帧便于：

- 区分多个 Stream
- 并发传输
- 流量控制
- 错误检测
- Header 压缩

需要注意：

> HTTP/2 只是传输格式变化了，HTTP 方法、状态码和语义基本没变。

例如仍然使用：

```
GET
POST
PUT
DELETE
200
404
500
```

## 4. Header 压缩

HTTP 请求经常携带大量重复 Header：

```
Host: example.com
User-Agent: ...
Cookie: ...
Authorization: ...
Accept: ...
```

HTTP/1.1 每次请求通常都要重复发送。

HTTP/2 使用 **HPACK** 对 Header 进行压缩，并维护动态表。重复的 Header 可以使用索引表示，从而减少传输数据量。

例如第一次发送：

```
Authorization: Bearer abcdef
```

后续可能只需要发送：

```
使用动态表中的第 62 项
```

## 5. 队头阻塞的区别

### HTTP/1.1 应用层队头阻塞

在一条 HTTP/1.1 连接中：

```
请求 A
请求 B
请求 C
```

如果 A 的响应很慢，B 和 C 往往也需要等待。

### HTTP/2 解决了 HTTP 层队头阻塞

HTTP/2 中 A、B、C 属于不同 Stream，可以交错传输。A 慢了，不一定会阻止 B 和 C 的 HTTP 帧发送。

但 HTTP/2 仍然运行在 TCP 上，所以仍存在 **TCP 层队头阻塞**。

假设一个 TCP 数据包丢失：

```
TCP 包 1
TCP 包 2：丢失
TCP 包 3
TCP 包 4
```

即使包 3 和包 4 属于其他 HTTP/2 Stream，TCP 也必须等待包 2 重传后，才能按序向上层交付。

因此：

```
HTTP/2 解决了 HTTP 层队头阻塞
但没有解决 TCP 层队头阻塞
```

HTTP/3 使用 QUIC，才进一步解决这个问题。

## 6. HTTP/2 和 gRPC 的关系

gRPC 通常基于 HTTP/2，因为 HTTP/2 提供：

- 多路复用
- 二进制分帧
- 双向流
- 长连接
- Header 压缩
- 单连接承载多个 RPC

例如 gRPC 双向流：

```
客户端持续发送消息
服务端持续发送消息
双方可以同时发送
```

## 7. HTTP/2 是否一定使用 HTTPS

从协议规范角度：

- `h2`：基于 TLS 的 HTTP/2
- `h2c`：明文 HTTP/2

实际浏览器通常只支持通过 HTTPS 使用 HTTP/2，即：

```
TCP
↓
TLS
↓
HTTP/2
```

服务端内部通信或 gRPC 可以使用明文 HTTP/2：

```
grpc://127.0.0.1:50051
```

这种通常相当于 h2c 场景。
